# v0.4 Threat Model — AI Debate Arena

Status: **review artifact for the v0.4 gate (F7-23 / F10-25)** — written 2026-09-11.
This document describes the security posture of the local-first app as it
exists today. It is deliberately explicit about what is **not** implemented.

Scope: `@arena/web` (Next.js server + API routes), `@arena/debate-engine`
(contracts, runner, challenge/evidence/sandbox adapters), `@arena/ai`
(provider factory), local file stores under `~/.ai-debate-arena` and the
gitignored `.data/` fallback. Out of scope: any hosted deployment (none is
supported — see [Residual risks](#residual-risks)).

## Assets

| Asset | Where it lives | Impact if compromised |
| --- | --- | --- |
| Provider API keys | `providers.json` (`0600`, server-only store) | Direct billing/abuse of the user's provider accounts. |
| Redacted provider hints (`apiKeyHint`) | API responses, browser memory | Low: truncation of the key only. |
| Match records (transcripts, verdicts, metrics) | `<home>/.ai-debate-arena/matches/*.json` or `.data/matches` (`0600`) | Disclosure of debate content the user may consider private; tampering would corrupt exported/re-judged history. |
| Evidence packets + source snapshots (hash-pinned) | Inside match records | Tampering could make fabricated evidence look hash-verified on export. |
| Source consents + access audits | Inside match records | Forgery would fake provenance of external-looking evidence. |
| Prompt/rubric/policy versions + config snapshots | Match records | Tampering breaks reproducibility claims, not confidentiality. |
| The user's local machine | — | Any server-side code execution (current or future adapters) runs with full Node process rights. |

## Trust boundaries

1. **Browser ↔ local Next.js server.** The API (`/api/*`) trusts any client
   that can reach it. There is no authentication, no CSRF protection, and no
   origin checking. This is only acceptable because the documented startup
   binds to `127.0.0.1` (loopback). Any process on the machine — and any
   website doing requests to `http://127.0.0.1:3000` from the user's browser —
   is inside this boundary until auth/CSRF exist.
2. **Local server ↔ provider endpoints.** The server makes outbound calls to
   user-configured OpenAI-compatible base URLs using stored keys.
3. **User-supplied evidence / source snapshots ↔ model prompts.** Evidence is
   attacker-influenced data; prompts must treat it as untrusted.
4. **Model output ↔ match state.** Judge and agent outputs are parsed with
   strict schemas before they may touch match state; a model is not an
   authority.
5. **Local files ↔ server.** Match/provider stores are read and written by the
   server under advisory locks; no other trust domain is assumed.

## Prompt injection

- Evidence (pasted text, local files, future source snapshots) is rendered
  only into **user** prompts, never system prompts, via the shared
  untrusted-evidence block (`packages/debate-engine/src/prompts/evidence-block.ts`):
  explicit BEGIN/END delimiters, a "DATA ONLY, never instructions" preamble,
  JSON-string-escaped content (raw newlines become `\n`, control characters
  cannot break out), bounded render budget with an explicit truncation marker.
- Agent and judge system prompts repeat the rule: evidence cannot change role,
  motion, rubric, or instructions (`prompts/challenge-prompt.ts`).
- Items render as `unverified` regardless of any status a source claims.

Residual: an LLM can still follow instructions smuggled into evidence despite
framing (injection is probabilistic, not solved). Delimiters cannot be forged
because content is JSON-escaped, but semantic manipulation (e.g. "grade A
higher") is always possible. Mitigation is bounded impact: evidence influences
an advisory judge, never executes anything and never reaches provider
configuration.

## Provider SSRF / exfiltration

- The **only** outbound HTTP from the match path is to the provider base URL
  the user configured themselves (`provider:add` / Manage providers), via
  `@ai-sdk/openai-compatible` / `@ai-sdk/openai`. The user choosing
  `http://169.254.169.254/` or an internal host as a "provider" is possible
  and is **not validated away** — it is the user's own machine and their own
  choice; there is no multi-tenant boundary to protect.
- Debater prompts contain only topic, position, rules, history, and rendered
  evidence. **API keys never enter prompts** and never appear in client
  responses (redaction is enforced by tests on the API surface).
- A malicious evidence packet can try to make a debater emit exfiltration
  instructions; the maximum leak is text into the provider transcript the user
  already trusts with their prompts. There is no tool, fetch, or URL-loading
  capability reachable from a model response.
- The `opencode-gateway` helper only adds static headers to a user-chosen
  base URL; it does not widen reachability.

Residual: no allow/deny list or scheme/host validation exists on provider base
URLs; if this app ever gains multi-user or hosted operation, this must be
added before anything else.

## Source consent / replay

The source-adapter slice (contracts + validation, plus the server-side HTTPS
source-fetch host below):

- `SourceConsent` is server-issued and server-derived: single-use `consentId`,
  adapter id **and exact version**, match/request binding, exact approved
  reference, copied capability grants, `confirmedByUserAction: true`, and an
  expiry. The client can never choose ids, grants, or expiry
  (`packages/types/src/source-adapters.ts`).
- `validateSourceGate` + `source-adapter-ingest.ts` re-validate the manifest,
  consent, and gate; **replaying a consent under a different
  id/match/request/reference or expired consent is rejected**. Snapshots are
  hash-pinned: ingest recomputes SHA-256 and UTF-8 byte counts from the exact
  bytes and rejects declared values that disagree. Audits are persisted per
  match without content or secrets.

### Server-side HTTPS source-fetch host (v0.4, server-only)

`apps/web/src/shared/server/source-fetch.ts` (`fetchSourceCapture`) performs
ONE bounded, consent-gated HTTPS capture of the exact consented reference.
Status (exact): the **host module, consent-gated API route, explicit capture UI,
and tests exist** — F10-09 is complete for the local v0.4 slice. Capture remains
one-shot, snapshot-only, untrusted, and unavailable without explicit user
confirmation. Implemented limits:

- The existing source gate (`validateSourceGate`) runs **before any socket**:
  strict manifest/consent schemas, explicit user action, granted, unexpired,
  exact adapter id/version, exact match/request/reference binding,
  capabilities covered, required permissions granted. `net.fetch` must be
  granted even if the manifest does not require it (deny-by-default).
- HTTPS only: `https:` scheme, no userinfo, port only 443 (default or
  explicit), hostname policy rejecting IP literals (WHATWG-normalized forms
  included), `localhost`/`.localhost`, malformed labels, control/percent
  hosts. Consent reference vs request reference must be string-identical AND
  origin-identical; otherwise no socket is opened.
- Explicit pinned `undici` (7.29.1) + `ipaddr.js` (2.5.0) dependencies; a
  dedicated one-shot `Agent` per capture (never the global dispatcher, never
  proxy env agents). The agent connects through a custom DNS lookup that
  resolves **all** records with `dns.lookup(all: true, verbatim: true)` and
  fails the connection if **any** record is non-public
  (`classifySourceIp` denies loopback, RFC1918, link-local — AWS/GCP metadata
  `169.254.169.254`, unique-local — AWS IPv6 metadata `fd00:ec2::254`,
  multicast, unspecified, IPv4-mapped IPv6 (evaluated on the embedded IPv4),
  NAT64 `64:ff9b::/96` + `64:ff9b:1::/48`, 6to4 `2002::/16`, Teredo
  `2001::/32`, carrier-grade NAT (Alibaba metadata space), Azure platform
  metadata `168.63.129.16`, documentation, benchmarking, and reserved
  ranges). Validation runs on **every** connection attempt, including every
  redirect hop.
- Manual redirects only: max 3 hops, each re-validated (HTTPS-only — no
  downgrade, same consented host only, no userinfo/IP literals, loop
  detection); redirect bodies are always cancelled.
- Fixed safe request headers only: bounded `accept`, `accept-encoding:
  identity`, fixed bounded `user-agent`. No Cookie/Authorization/API keys,
  no provider env values, nothing copied from the caller.
- Dedicated timeouts: DNS, connect, headers, inter-chunk body, and an overall
  wall-clock deadline (AbortController). Bodies are streamed with a hard
  decoded-UTF-8 byte cap (16 KiB, matching `SOURCE_ADAPTER_LIMITS`); nothing
  unbounded is buffered.
- Only `text/plain` and `text/markdown` are accepted; `text/html` is
  accepted **only when the caller explicitly opts in** (`allowHtmlText`),
  and is stripped to plain text server-side, treated strictly as untrusted
  text (never rendered/executed). Capture hash and exact UTF-8 byte count
  are recomputed server-side — remote headers/hash/freshness are never
  trusted. No caching, no refresh, no state.
- Every failure is a safe reason code (`consent-*`, `dns-*`, `scheme-not-https`,
  `ip-literal-host`, `redirect-*`, `timeout`, `body-too-large`, …). Raw
  network errors, URLs, DNS records, and resolved addresses are never exposed.

Source-host residual (stated plainly): this host narrows — but cannot
eliminate — the outbound-HTTP trust boundary. A consented host is still
attacker-influenced *content*: the captured text is untrusted (rendered as
evidence only), and a compromised consented host could serve fabricated
content that will be hash-pinned as "verified capture". Consent is still not
authentication, and there is still no allow-list of "approved" source hosts —
any https host a user explicitly consents to is reachable. The single-use
property of `consentId` is enforced by callers/stores, not by this module.

Residual (stated plainly): **local consent is not authentication.** Nothing
verifies which human clicked — any local browser page can drive the UI, and
the "user action" is only as meaningful as the single local user assumption.
Consent freshness is clock-based and trusts the local clock (bounded skew).

## Sandbox capabilities

- `SandboxAdapter` contracts (`sandbox-adapter-contract.ts`): deny-by-default
  capability model — network, filesystem, process execution, and secrets are
  explicit capabilities granted by the server-side `SandboxCapabilities`,
  never by the client. Limits (input/output bytes, timeout) are bounded;
  error messages are sanitized (no paths, no raw exceptions); every terminal
  result requires a cleanup receipt.
- The pure, deterministic SHA-256 content-integrity proof adapter (no I/O)
  remains the default and runs in-process.
- **Local worker host (`@arena/sandbox-host`, F10-19/F10-24):** a narrow,
  fail-closed host runs ONE allow-listed, server-owned deterministic worker
  inside a Windows Job Object (kill-on-close, no-breakaway, active-process
  and per-process memory caps) with a behavioral containment preflight,
  host-owned wall-clock watchdog, output cap with kill, verified process-tree
  death, retried temp-dir cleanup, and host-attested cleanup receipts.
  Without a proven preflight (non-Windows, missing FFI, unverifiable
  containment) it reports `unavailable` and spawns nothing. There is no
  generic command runner and no client-controlled executable, args, env, or
  paths. See `docs/security/sandbox-host.md` for the full analysis.

Residual (stated plainly): **a Job Object is containment and resource
governance, not a filesystem/network security boundary.** The worker runs
with full user rights; safety rests on it being server-owned, allow-listed,
deterministic code — not on the job jail. Do not point this host at
untrusted code without real isolation (restricted token/AppContainer or the
remote-sandbox adapter F10-20).

## Storage and locking

- Provider store and match records are written `0600` (dir `0700`) via
  unique temp file + atomic rename; failed writes remove their temp file.
  Windows POSIX-mode emulation is best-effort — a multi-user Windows host
  should not be assumed isolated per user.
- Cross-process advisory lock (`record-lock.ts`): atomic exclusive create
  (`wx`), per-resource lock files, stale takeover after 10 min, release in
  `finally`. Provider store mutations and challenge lifecycles hold it.
- Match ids are strictly validated before they touch paths; match records are
  schema-validated on every read.
- The match-store fallback (`.data/matches`) is gitignored and only used when
  the home store is unavailable.

## Mitigations already implemented

- Server-only secret storage (`0600`), key redaction on every API response,
  safe typed provider errors (no key/URL leakage — tested).
- Evidence bounded (size/type/count/byte caps, body cap), rendered untrusted,
  isolated from system prompts, adversarial prompt tests.
- Strict zod schemas at every boundary (providers, match config/events,
  verdict, evidence, source adapters, sandbox) with unknown-field rejection.
- Deny-by-default sandbox capability contract; deterministic-only adapter.
- Challenge budgets finite, idempotent, concurrency-locked; verdict preserved
  on any challenge/evidence/sandbox failure.
- Loopback-only documented startup (`127.0.0.1` for dev and production
  `next start`; asserted by `apps/web/src/shared/config/startup.test.ts`).

## Residual risks

1. **No authentication, CSRF, or origin checks.** The whole model rests on
   loopback binding. `0.0.0.0`/LAN exposure is **unsupported** until auth,
   CSRF, and a pairing flow exist. DNS-rebinding or a hostile local process
   defeats this entirely.
2. **External source capture is local and opt-in only.** The server-side
   consent-gated HTTPS source-fetch host and completed-match route are wired
   (`apps/web/src/shared/server/source-fetch.ts` and
   `apps/web/src/app/api/matches/[id]/sources/route.ts`), with an explicit UI,
   SSRF-hardened URL/DNS/redirect/body policy, snapshot-only storage, and
   focused tests. There is no automatic refresh or remote deployment support.
   Provider base URLs remain unvalidated user choices.
3. **Process sandbox is containment-only.** The local worker host (F10-19)
   proves and enforces process-tree containment, resource limits, timeouts,
   and cleanup on Windows, but the worker runs with full user rights — the
   job does not restrict filesystem or network access. Safety depends on the
   worker staying server-owned and capability-free.
4. **Model adjudication is not truth.** Judge/challenge verdicts are model
   output, bounded and schema-validated, but they can be wrong or biased; the
   UI labels outcomes as assessed, never as fact. Do not treat evidence
   statuses as ground truth either — items are `unverified` by default and
   only rules ever upgrade them.
5. **Local consent is not authentication** (see above).
6. **Prompt injection is mitigated, not solved** (see above).
7. Provider base URLs are unvalidated user choices; a hostile "provider" gets
   the full debate context and could return any content.
8. Windows file permissions are best-effort; secrets on shared machines are
   readable by same-user processes by design of the OS.
9. The eval/CLI scripts (`judge-eval.mjs`, `provider-add.ts`) run with the
   user's full rights and trust the local provider store; no additional
   hardening exists or is needed while they stay local-only.
